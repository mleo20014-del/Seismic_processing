# Playback-контроллер, потоки/синхронизация, бенчмарк

## Менеджер воспроизведения (playback controller)

Работает только через `ChunkSource`, не зная конкретной реализации:

```python
class PlaybackController(QObject):
    def __init__(self, source: ChunkSource, gpu_texture_binding: "RegisteredImage"):
        ...
    # state machine: playing / paused / seeking / buffering
```

- **Скорость воспроизведения** — интервал таймера, с которым запрашивается следующий timestep
  через `source.get_chunk(...)`.
- **Децимация количества точек** — параметр `decimation_stride` в `ChunkRequest`, передаётся до
  источника: для Local — влияет на шаг CUDA-кернела записи в текстуру; для Cloud/Cluster — может
  влиять на то, что сервер присылает изначально более грубый/прореженный чанк, экономя трафик.
- **Пауза/перемотка** — читает из локального GPU-кэша (кольцевой буфер последних N timestep'ов на
  GPU), если пользователь скраббит недалеко от текущей позиции; при скачке далеко — сброс кэша и
  приоритетный запрос нового чанка (`is_stale=True` на предыдущем кадре, пока грузится новый) с
  индикацией через лёгкий сигнал прогресса, не блокировка UI.
- **Bandwidth-aware поведение (Cloud/Cluster):** если `capabilities()["max_fps"]` ниже желаемой
  пользователем скорости воспроизведения, контроллер автоматически повышает `decimation_stride`
  или снижает целевой FPS, вместо накопления очереди непроигранных чанков — предотвращает
  «долгую раскачку» интерфейса при слабом канале.
- Реализуется как конечный автомат (state machine) с состояниями: `playing`, `paused`, `seeking`,
  `buffering` — статус транслируется в QML только как строка/enum для индикатора, не как повод
  блокировать интерфейс.

## Потоки и синхронизация

- Чтение чанков (диск, Zarr/HDF5) — в `ThreadPoolExecutor`/отдельном процессе.
- Сетевые `ChunkSource` (Selectel/Cluster) — WebSocket-клиент работает в `asyncio`-event loop в
  отдельном потоке от Qt event loop; связь с Qt/QML — через `Signal`, эмитируемый из
  `asyncio`-потока в основной поток (`QMetaObject.invokeMethod` с `Qt.QueuedConnection`, если
  сигнал эмитируется не из потока GUI).
- CUDA-кернелы — выполняются на отдельном CUDA-стриме, синхронизируются с рендер-потоком Qt через
  событие (`cuda.Event`) перед `map()`/`unmap()`, чтобы не читать текстуру в процессе записи.
- **Правило:** RHI `render()` никогда не ждёт диск/сеть. Если новый чанк не готов — рисуется
  последний валидный кадр (`is_stale=True`), ожидание идёт асинхронно.

## Замер и калибровка сетевых источников

`scripts/bench_chunk_source.py` — обязательный шаг перед фиксацией целевого FPS/decimation для
Cloud/Cluster: измеряет `latency_ms_p50/p95`, `throughput_MB_s`, и на основе этого предлагает
безопасный `decimation_stride` и целевой FPS для конкретного канала. Результаты записываются в
`capabilities()` конкретного `ChunkSource`-инстанса при инициализации, не хардкодятся.

## Финальная проверка перед PR по interop-слою

- Нет ни одного `cudaMemcpyDeviceToHost`/`.get()`/`.cpu()` на пути «вычисление → экран».
- `RegisteredImage` создаётся один раз на текстуру, не пересоздаётся каждый кадр.
- Есть явный `unmap()` на каждый `map()`, включая пути с исключениями (`try/finally`).
- Проверено поведение при резкой перемотке (seek) — не блокирует UI дольше одного кадра.
- Новый `ChunkSource` реализует полный интерфейс (`get_chunk`, `prefetch`, `capabilities`) и
  покрыт тем же набором тестов playback-контроллера, что и существующие реализации.
- Логика decimation/скорости покрыта unit-тестами без реального GPU (мокается CUDA-слой и
  сетевой транспорт).
- Для сетевых источников — формат сериализации чанка задокументирован в docstring класса и
  совпадает по обе стороны (клиент/сервер).
