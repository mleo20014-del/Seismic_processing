# AGENTS.md — Инструкции для AI-агентов

> Этот файл задает правила и ограничения разработки, архитектуру приложения, базовый технологический стек для ИИ-ассистентов, работающих с этим репозиторием.

## 0. Обозначения и пояснения
Слово "системный" означает работающий на уровне всего проекта, а не частный

Слова "приложение", "репозиторий", "проект" означают одно и то же

## 1. Обзор проекта
* **Назначение:** Геофизическое desktop-приложение на python для задач обработки сейсмических данных.
* **Общие сведения:** Разрабатывается приложение-конструктор, которое разделено на 5 частей.

## 2. Разделение приложения на части/слои
1. **UI-часть**. Отвечает исключительно за визуальную оболочку приложения, наполненность кнопками и вкладками. Отвечает за отправку сигналов в другие части приложения.
Ничего не знает о логике выполнения.
2. **CORE-часть**. Это брокер сигналов/сообщений. Выполняет оркестрацию процессов. Отвечает за общение частей приложения с "клиентом" с помощью JSON-файлов.
Отправка запросов в хранилище, валидация типов перед отправкой заданий/сигналов на выполнение с помощью Pandantic. Способен обрабатывать множество сигналов параллельно и последовательно. Под капотом работает RabbitMQ.
4. **VIEWER-часть**. Отвечает исключительно за визуализацию поступающих чанков MDIO от хранилища STORAGE.
5. **STORAGE-часть**. Принимает сигнал от CORE и отправляет сейсмические данные чанками MDIO в VIEWER или на расчёт на GPU/CPU компьютера пользователя, на железо Selectel для расчёта задания.

## 3. Архитектура и внутреннее устройство файлов
Базовые директории, которые появляются после git-clone проекта из репозитория:

`/app` — хранится логика, код выполнения для различных менеджеров, контроллеров, пакетов приложения, системных предустановленных нод и так далее.

`/config` — хранятся все default конфигурации параметризация логики из `/app`, конфигурации default проекта при запуске.

`/settings` — хранятся default настройки приложения (например настройки для отображения ui, настройка брокера CORE, настройка api подключений и так далее).

`/ui` — хранится вся default QML оболочка приложения (всё что даёт отображение на экран).

`/core` — хранится логика работы приложения, а не отдельных его модулей/плагинов.

`/docs` — хранится вся документация для прочтения человеком. Этой директорией управляет отдельный ИИ-агент под руководством человека.

`/ai` — хранятся все правила и инструкции по разработке этого приложения (обращайся сюда для дополнительного контекста), а также ADR-журналы, которые создаются после каждого шага разработки.

`/scripts` — хранятся вспомогательные системные скрипты, которые не являются частью проекта, но помогают его работе.

`/i18n` — хранятся файлы .ts и .qm для задач интернационализации.

`/.github` — хранятся CI/CD yaml инструкциии разделённые по выполняемым задачам. GitHub Actions.

`/core` — директория где хранится логика работы приложения, а не отдельных его модулей/плагинов,

`/pytest` — директория где хранятся скрипты для проведения тестов работы проекта,

`/logs` — ошибки при запуске и работе приложения. Сюда не включены ошибки полученные в процессе взаимодействия с приложением

Директории, которые создаются при взаимодействии при работе с приложением:

`/data` — директория где хранятся локально созданные/загруженные файлы .segy, .sgy, .segd, .zarr, .txt и прочие. Локальное хранилище с доступом по паролю пользователя.

`/user` — директория где хранятся всё, что создаётся пользователем в процессе работы с приложением (персонализация ui, конфиги, пароли, кастомные созданные пользователем ноды/плагины). Кроме того, что попадает в директорию `/data`.

`/mcp` — директория где хранятся настройки для подключения локального LLM-помощника с помощью стандарта mcp-сервера к ручкам приложения.

## 3. Технологический стек (UI/Rendering)

| Слой | Технология | Причина выбора |
|---|---|---|
| GUI-каркас | PySide6 (Qt 6.7+) + QML/Qt Quick | Нативная Python-совместимость без C++ компиляции пользовательского кода |
| Стиль контролов | Qt Quick Controls 2, стиль `Basic` с точечным переопределением | Паттерн Meshroom — полный визуальный контроль без переписывания движка контролов |
| Кастомный рендер (2D и 3D) | `QQuickRhiItem`, backend закреплён на **OpenGL** | Единый пайплайн для 2D-графиков и 3D-объёма; зрелый CUDA-interop именно с OpenGL |
| Шейдеры | Ручной GLSL → компиляция в `.qsb` через `qsb` | Максимальный контроль над рендерингом волнового поля |
| GPU-вычисления | CUDA (существующий стек проекта) | Уже используется для FDTD/обучения сетей |
| Zero-copy interop | CUDA↔OpenGL через PyCUDA (`pycuda.gl`) | Единственный зрелый Python-путь к zero-copy без написания C++/Vulkan-моста |
| Источник данных для рендера | Абстракция `ChunkSource`: Local / Selectel / Cluster | Единый playback/rendering код независимо от того, где физически считаются данные |
| Нод-граф | Кастомный QML `GraphEditor` (модель Meshroom), Python-модель на `QAbstractItemModel` | Постепенная замена `NodeGraphQt`, консистентность с остальным UI |
| Данные | Zarr / HDF5, потоковые чанки, `np.memmap` | Принято ранее, не пересматривается в рамках этого документа |
| Offline QA-визуализация | PyVista/VTK в отдельных Jupyter-скриптах | Только для проверки моделей вне продакшен-рендера, не входит в дистрибутив |
| Live preview | `pyside6-qml` / `qmlscene` | Итерация по QML без перезапуска Python-процесса |
| ОС | Linux (разработка) + Windows (целевая) | Кроссплатформенность обязательна |

### Явно отклонённые технологии

- **Qt Widgets / Qt Designer `.ui`** — устаревший подход, весь новый UI-код только на QML.
- **Qt3D** — вытесняется Qt Quick 3D/RHI, не используется для нового кода.
- **VTK / PyVista как основной рендер-движок** — нет встроенного zero-copy CUDA-interop; интеграция
  только через `QWidget`-путь (`QVTKRenderWindowInteractor`/`pyvistaqt.QtInteractor`), что рвёт единый
  QML-пайплайн; задокументированы регрессии производительности и баги связки с PySide6. Роль в
  проекте — только offline QA вне продакшен-рендера.
- **Qt Design Studio** — не нужен при ручной вёрстке QML в одиночку.
- **Qt Quick Compiler (qmlcc)** — не используется, QML остаётся интерпретируемым для hot-reload.
- **CUDA↔Vulkan external memory interop** — нет готовых Python-биндингов ни в PyCUDA, ни в CuPy;
  требует собственного C++/pybind11-моста.

## 4. Ключевые архитектурные решения (зафиксировано, не пересматривать без явного запроса)

1. **Единый рендер-пайплайн.** 2D (сейсмограммы, срезы, каротаж) и 3D (объём волнового поля)
   рисуются одним механизмом — `QQuickRhiItem` с собственными GLSL-шейдерами. 2D — частный случай
   3D с одним направлением обхода данных.
2. **RHI backend закреплён на OpenGL.** Переход на Vulkan пересматривается только вместе с
   пересмотром слоя interop (см. п.10 раздела 6).
3. **Zero-copy обязателен с первой итерации** на горячем пути «вычисление → экран». CPU-путь
   допустим только при первичной загрузке чанка с диска/сети до его переноса на GPU. Zero-copy
   технически возможен только внутри одного физического GPU/процесса — он никогда не «пересекает
   сеть»; при Cloud/Cluster он начинается с момента, когда чанк уже физически лёг в GPU-память клиента.
4. **Данные волнового поля — регулярная 3D-сетка (voxel grid).** Рендер через raymarching-шейдер
   поверх 3D-текстуры с transfer function (LUT). Не point cloud/instancing.
5. **Шейдерная дисциплина.** GLSL-исходники — файлы-ассеты в репозитории, не инлайн-строки в
   Python. Компиляция в `.qsb` — отдельный шаг сборки, не runtime продакшена.
6. **Тема и стиль — путь Meshroom.** Единый QML-singleton `Theme.qml`/`Colors.qml`; переопределяются
   точечно только реально используемые базовые контролы.
7. **Нод-граф мигрирует на QML.** `NodeGraphQt` — временное решение, целевая архитектура — QML
   `GraphEditor` с моделью на `QAbstractItemModel`.
8. **UI-поток не блокируется никогда.** Тяжёлые операции (диск/сеть/CUDA/декодирование) — вне
   UI-потока. В QML попадают только указатели на GPU-ресурсы и лёгкие метаданные.
9. **Управление воспроизведением** (скорость, децимация, пауза/перемотка) — на уровне Python
   `PlaybackController`, не через QML-анимации напрямую.
10. **Единая абстракция `ChunkSource`.** Рендерер и playback-контроллер не знают, откуда физически
    пришёл чанк. Три поддерживаемых реализации: Local, Selectel (cloud), Cluster (корпоративный).
11. **Сетевой канал — определяющий фактор для Cloud/Cluster.** Пропускная способность и задержка
    ограничивают реалистичный FPS и decimation; замеряются эмпирически, не задаются теоретически.

## 5. Правила чистоты и производительности кода

### MUST DO
- Шаги разработки разбиты на фазы для последовательного выполнения, поэтому для перехода на следующую запроси у меня подтверждение
- После завершения фазы разработки, делай запрос у меня на проведение тестов. После подтверждения читай последнюю или наиболее актуальную версию скиллов: `/ai/TEST/skills/` и правил `/ai/TEST/rules/`. Выполняй тесты и продолжай работу дальше в соответствии с планом
- 
- Всегда освобождать GPU-ресурсы и CUDA-хендлы явно при уничтожении `QQuickRhiItem`.
- Всегда делегировать логику тяжелее тернарного выражения из `.qml` в Python или шейдер.
- Всегда коммитить обновлённый `.qsb` вместе с изменённым `.glsl`-исходником в одном коммите.
- Всегда реализовывать переключение `Local`/`Selectel`/`Cluster` через конфигурацию/DI, без правок
  кода рендерера или playback-контроллера.

### MUST NOT DO
- Не выполнять NumPy/CPU round-trip для данных, уже находящихся на GPU, на горячем пути отрисовки.
- Не смешивать логику 2D-графика и 3D-объёма в одном `QQuickRhiItem`-подклассе.
- Не вызывать блокирующие операции (диск, сеть, тяжёлый CUDA-кернел) напрямую в слоте, вызываемом из QML.
- Не хардкодить цвета/отступы в `.qml`-компонентах вместо `Colors.qml`/`Theme.qml`.
- Не переносить архитектурные решения этого файла на FDTD/ML-слой без явного запроса владельца проекта.

## 8. Не делать без явного запроса

- **Выбор упаковщика** (PyInstaller / Nuitka / иное) — агент обязан спросить пользователя перед
  реализацией, самостоятельно не выбирает.
- **Переход RHI backend на Vulkan.**
- **Полная/частичная замена `NodeGraphQt`** — сроки и объём миграции на QML `GraphEditor`.
- **Headless server-side рендеринг для Cluster** (видеопоток вместо `ChunkSource`) — отдельная
  архитектура, не проектируется заранее.
- **Точный формат сериализации/сжатия чанков** для Cloud/Cluster (float16 vs квантованный int16) —
  фиксируется только после эмпирического замера сети (`bench_chunk_source.py`).
