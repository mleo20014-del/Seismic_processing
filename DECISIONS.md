## D001 | 2026-09-14 | active | Выбор упаковщика — PyInstaller

**Решение:** для сборки дистрибутива используется PyInstaller, а не Nuitka.

**Обоснование:** владелец проекта явно передал выбор на усмотрение разработчика («используй
наиболее удобный»). PyInstaller выбран по трём причинам: (1) готовые community-hooks под PySide6/
Qt6 снижают риск сломанной сборки QML-ресурсов; (2) для нативной зависимости PyCUDA конфигурация
через `--add-binary`/`datas` более предсказуема, чем ручная настройка Nuitka под CUDA toolkit;
(3) более быстрый цикл отладки сборки на раннем этапе важнее выигрыша в скорости runtime, который
даёт Nuitka. Пересмотр возможен, если на Фазе 6 профилирование покажет неприемлемый размер/время
старта дистрибутива.

**Требует подтверждения:** нет (делегировано явно), но будет упомянуто в отчёте по возвращении.

## D003 | 2026-09-14 | active | Backend вычислений — только Local на первые 6 месяцев, с UI-заготовкой переключателя

**Решение:** `SelectelChunkSource`/`ClusterChunkSource` реализуются как классы с полным
интерфейсом `ChunkSource`, но методы `get_chunk`/`prefetch` поднимают явный `NotImplementedError`
с понятным для пользователя сообщением. В UI чекбокс/переключатель способа расчёта присутствует
и визуально доступен, но недоступные варианты явно помечены («доступно позже»), выбор блокируется
без сбоя интерфейса.

**Обоснование:** явное указание — «вычисления в Selectel и на кластерах откладываем на полгода...
но не хардкодим переменные, а проектируем так, чтобы можно было переключить в UI чекбокс».

**Требует подтверждения:** нет.

основной)». Qt Linguist выбран как стандартный, наименее рискованный путь для QML-проекта на
PySide6, не требующий стороннего i18n-фреймворка.

**Требует подтверждения:** нет.

## D008 | 2026-09-16 | active | GLSL-профиль шейдеров: 100 es,120,330 вместо 100 es,120,150

**Решение:** для компиляции `.qsb` используется профиль `--glsl "100 es,120,330"` вместо
`"100 es,120,150"`, упомянутого в `shader-and-raymarching.md`.

**Обоснование:** `QQuickRhiItem` требует `layout(location = ...)` в vertex-шейдерах — этот
qualifier недоступен в GLSL `150`. GLSL `330 core` поддерживает `layout qualifiers` и является
стандартным минимумом для OpenGL 3.3 Core Profile, на котором работает QRhi/OpenGL backend
приложения. Профили `100 es` и `120` остаются в наборе для совместимости с мобильными
платформами (хотя текущий target — только Desktop Linux/Windows с RTX 3050+).

**Требует подтверждения:** нет. При портировании на встраиваемые платформы с GLES 2.0
это решение пересматривается.

## D011 | 2026-09-16 | active | i18n (Qt Linguist) внедряется с Фазы 0, а не с Фазы 1

**Решение:** инфраструктура Qt Linguist (`.ts`/`.qm`, `QTranslator`, `qsTr()` в QML) внедряется
в Фазе 0, не откладывается на Фазу 1.

**Что реализовано в Фазе 0:**
- `app/main.py`: `QTranslator` устанавливается ДО создания `QQmlEngine` (порядок критичен).
- `ui/qml/main.qml`: все строки через `qsTr()`.
- `i18n/seismic_ru.ts` + `i18n/seismic_ru.qm`: переводы RU (2 финальных перевода).
- `i18n/seismic_en.ts` + `i18n/seismic_en.qm`: EN-каркас (source-язык, переводы пустые).
- `scripts/update_translations.py`: `lupdate` (сканирование) + `lrelease` (компиляция).
- CI: проверка наличия `.ts` файлов.

**Обоснование:** явное решение владельца — «внедряй i18n с фазы 0 (на базовом уровне. Это важное
решение владельца)». Закладывать i18n постфактум дороже, чем сразу писать `qsTr()` во всех
строках. D004 (i18n с Фазы 1) заменяется этим решением для инфраструктурного уровня.

**Требует подтверждения:** нет.
