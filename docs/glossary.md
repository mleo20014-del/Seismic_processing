Глоссарий терминов проекта
Краткое описание
Сводный глоссарий всех узкоспециализированных терминов, использованных в серии проектной документации (01_main, BACKEND, 03_architecture, 04_philosophy, 07_infrastructure_costs, 07_testing_and_performance). Термины сгруппированы по пяти тематическим блокам: маркировка документации, работа с LLM-агентами, архитектура ПО, инфраструктура и облачные вычисления, тестирование/производительность, и предметная область сейсморазведки. Документ живой — пополняется по мере появления новых терминов в новых статьях.
1. Маркировка документации
[FACT] — Тег, обозначающий проверенное, подтверждённое источником утверждение в тексте статьи.
[ASSUMPTION] — Тег, обозначающий предположение или оценку команды, не подкреплённую доказательствами на момент написания — требует проверки.
[DECISION] — Тег, обозначающий принятое и зафиксированное архитектурное или проектное решение.
ADR (Architecture Decision Record) — Короткая атомарная запись формата «выбрали X вместо Y, потому что Z» — фиксирует одно архитектурное решение отдельно от нарративных статей серии. Хранится в каталоге adr/.
Wayfinder — Методология разбиения слишком крупной задачи документирования или разработки на этапы, каждый из которых проходит отдельный цикл гриллинга перед сведением в единую спецификацию.
См. также: 04_philosophy
2. Работа с LLM-агентами
LLM-помощник — Встроенный в приложение ассистент на основе языковой модели, обеспечивающий навигацию по проекту на русском языке, помощь при ошибках и автосуммаризацию модулей.
См. также: 01_main
RAG (Retrieval-Augmented Generation) — Архитектурный паттерн, при котором языковая модель дополняет ответ результатами поиска по внешней базе знаний (в проекте — по документации) перед генерацией финального текста.
Подагент (subagent) — Вспомогательный агент, выполняющий изолированную задачу и возвращающий в основную сессию только итоговые выводы, а не полный ход рассуждений — предотвращает засорение контекста основной сессии.
См. также: Kontseptsiia-razrabotki-s-II, 04_philosophy
Оркестрация — Управление последовательностью и распределением задач между несколькими агентами и человеком-разработчиком в рамках одного процесса разработки.
Гриллинг (Grilling) — Структурированная сессия вопросов от агента к человеку, превращающая размытое намерение в дерево конкретных, согласованных решений перед началом реализации задачи.
См. также: 04_philosophy
Frontier-вопрос — Вопрос, который агент может сформулировать уже на основе имеющегося контекста в текущем раунде гриллинга — граница уже проясненного и ещё неясного.
См. также: 04_philosophy
Shared understanding — Явно подтверждённое человеком согласованное понимание задачи, которым завершается сессия гриллинга.
См. также: 04_philosophy
Smart Zone / Dump Zone — Smart Zone — объём контекста агента (обычно несколько сотен тысяч токенов), при котором сохраняется высокое качество работы; Dump Zone — состояние деградации агента при чрезмерном разрастании контекста задачи.
См. также: 04_philosophy
Handoff — Явная выгрузка результата работы агента в артефакт (.md-файл, код, отчёт) для передачи следующей сессии или другому агенту, вместо переноса полной истории диалога.
См. также: 04_philosophy
Тикет Human-in-the-loop — Тикет, затрагивающий архитектуру, интерфейс или бизнес-логику и требующий обязательного участия человека в процессе выполнения, а не только финального ревью.
См. также: 04_philosophy
AFK-тикет — Небольшая изолированная задача без влияния на ключевую логику, которую агент выполняет автономно; человек проверяет только финальный результат перед слиянием.
См. также: 04_philosophy
Vertical slice (вертикальный срез) — Способ разбиения задачи на тикеты по законченной функциональности (фиче), а не по техническому слою — каждый тикет даёт видимый работающий результат.
См. также: 04_philosophy
TechLead-агент — Роль в команде агентов, отвечающая за генерацию идей и системный анализ решений (Perplexity, Claude), в тесной связке с человеком-разработчиком.
См. также: Kontseptsiia-razrabotki-s-II
3. #### Архитектура программного обеспечения
Node-based / нодная архитектура — Способ организации обработки данных как графа связанных между собой узлов (нод), каждый из которых выполняет одну операцию и передаёт результат следующему узлу.
См. также: 03_architecture, BACKEND
NodeContext — Объект, содержащий состояние и данные, доступные узлу во время выполнения; используется для проверки готовности входов узла.
См. также: BACKEND
Workflow JSON — Представление рабочего процесса для графического редактора: позиции узлов на холсте, связи, версии, метаданные интерфейса.
См. также: 03_architecture
Prompt graph / ComputeGraph — Нормализованное представление графа для выполнения расчёта — только узлы, связи и параметры, без UI-метаданных.
См. также: 03_architecture
NodeSchema — Декларативный контракт узла обработки: типы входов и выходов, обязательные параметры, версия схемы.
См. также: 03_architecture
JobStatusView — Агрегированное представление прогресса расчёта для интерфейса, производное от состояния очереди и истории выполнения.
См. также: 03_architecture
Топологическая сортировка / расстановка — Алгоритм упорядочивания узлов графа, при котором каждый узел выполняется только после того, как готовы все его входные зависимости.
См. также: 03_architecture
Ленивый вход (lazy input) — Входной параметр узла, который запрашивается только тогда, когда действительно понадобится для выбранной ветки алгоритма, а не заранее.
См. также: 03_architecture
Частичное выполнение (partial execution) — Выполнение только той части графа, которая необходима для получения выбранных пользователем выходных узлов, без пересчёта всего пайплайна.
См. также: 03_architecture
IsChangedCache / HierarchicalCache — Механизм кэширования результата узла, при котором выход переиспользуется, если входы (включая всю цепочку узлов-предков) не изменились с прошлого выполнения.
См. также: 03_architecture
ID-based кэширование — Кэширование по идентификатору или версии объекта данных (например, путь + время модификации файла), а не по содержательному хэшу самих данных — применяется, когда данные слишком тяжелы для контентного хэширования.
См. также: 03_architecture
Prestartup-хук — Скрипт, выполняемый до основной инициализации приложения (например, до импорта тяжёлых библиотек), используется для сборки расширений или загрузки весов моделей.
См. также: 03_architecture
VRAMState — Перечисление уровней доступной видеопамяти GPU, используемое диспетчером для решения, какую долю модели или данных держать на устройстве.
См. также: 03_architecture
Chunked-загрузка / chunking — Разбиение большого массива данных на части (чанки) для последовательной обработки, когда весь массив не помещается в доступную память целиком.
См. также: 03_architecture, BACKEND
Application shell — Совокупность прикладных подсистем приложения (управление пользователями, шаблонами, настройками, версиями), окружающих ядро выполнения расчётов.
См. также: 03_architecture
Pinned memory — Область оперативной памяти, зафиксированная операционной системой для ускоренной передачи данных на GPU без дополнительного копирования.
См. также: BACKEND, 03_architecture
non_blocking=True — Параметр асинхронной передачи данных на GPU, позволяющий CPU готовить следующий batch, пока GPU обрабатывает текущий.
См. также: BACKEND
Signals/slots (сигналы/слоты) — Механизм Qt (PyQt6) для потокобезопасной передачи событий из фонового потока расчёта в главный поток интерфейса без его блокировки.
См. также: BACKEND, 03_architecture
QThread — Класс Qt для выполнения кода в отдельном потоке, используемый в проекте для вынесения тяжёлых расчётов из главного потока интерфейса.
См. также: BACKEND
4. Инфраструктура и облачные вычисления
Pay-as-you-go — Модель оплаты облачных ресурсов по фактическому объёму использования (часы, гигабайты), без фиксированной абонентской платы.
См. также: 07_infrastructure_costs
S3 / Object Storage — Протокол и класс облачного хранилища для объектных (файловых) данных с доступом через REST API; в проекте используется для хранения сейсмических массивов и архивов.
См. также: 07_infrastructure_costs, BACKEND
Warm-хранение — Слой хранения для данных в процессе активной обработки — быстрый доступ, локальный Zarr-store на диске проекта.
См. также: BACKEND
Cold-хранение — Слой хранения для архивных, редко используемых данных — Zstd-сжатый контейнер, экономия места при сохранении возможности доступа.
См. также: BACKEND
Классы хранения Standard / Cold / Ice — Тарифные уровни объектного хранилища с разной стоимостью и скоростью доступа: Standard — активные данные, Cold и Ice — архив с постепенно уменьшающейся ценой и увеличивающейся задержкой доступа.
См. также: 07_infrastructure_costs
Исходящий трафик (egress) — Объём данных, передаваемых из облачного хранилища во внешнюю сеть; тарифицируется отдельно от хранения и особенно значим при работе вычислений и хранилища у разных провайдеров.
См. также: 07_infrastructure_costs
Латентность (latency) — Задержка при передаче данных между компонентами системы; критична при чтении чанков данных в цикле обучения модели или итеративной обработки.
См. также: 07_infrastructure_costs
GPU-часы / CPU-часы — Единица измерения потребления облачных вычислительных ресурсов, используемая для тарификации и расчёта интенсивности нагрузки (категории LIGHT/NORM/HARD).
См. также: 07_infrastructure_costs
TFLOPS — Показатель пиковой вычислительной производительности процессора (триллионов операций с плавающей точкой в секунду), используется для сравнения GPU по цене/производительности.
См. также: 07_infrastructure_costs
VRAM — Видеопамять GPU; объём VRAM ограничивает максимальный размер данных, которые можно обработать на устройстве без чанкинга.
См. также: 07_infrastructure_costs, 03_architecture
Локальность вычислений и хранения — Принцип размещения вычислительных ресурсов и хранилища данных у одного провайдера/в одном регионе для минимизации трафика и задержки между ними.
См. также: 07_infrastructure_costs
5. Тестирование и производительность
CI/CD (Continuous Integration/Continuous Deployment) — Практика автоматического запуска тестов, проверок и сборки при каждом изменении кода, снижающая ручную нагрузку на разработчика перед слиянием изменений.
См. также: 07_testing_and_performance
Регрессионный тест качества расчёта — Тест, сравнивающий результат обработки с заранее зафиксированным эталонным (baseline) выходом с заданной точностью, для обнаружения непреднамеренного изменения поведения алгоритма.
См. также: 07_testing_and_performance
Baseline (эталонные данные) — Заранее зафиксированный ожидаемый результат расчёта, с которым сравниваются новые версии кода в регрессионных тестах.
См. также: 07_testing_and_performance
cProfile / line_profiler / memory_profiler — Последовательность инструментов профилирования Python-кода: cProfile находит медленную функцию, line_profiler — медленную строку внутри неё, memory_profiler — пиковое потребление памяти.
См. также: 07_testing_and_performance
ASV (Airspeed Velocity) — Инструмент для бенчмаркинга Python-пакета на протяжении всей истории коммитов с автоматическим обнаружением регрессий производительности во времени.
См. также: 07_testing_and_performance
DCGM (NVIDIA Data Center GPU Manager) — Инструмент для непрерывного сбора детальных метрик состояния GPU (загрузка, температура, VRAM, ошибки) в промышленной эксплуатации.
См. также: 07_testing_and_performance
OOM (Out Of Memory) — Ошибка нехватки памяти (RAM или VRAM) при попытке обработать данные, превышающие доступный объём — основной риск при работе с тяжёлыми сейсмическими кубами без чанкинга.
См. также: 07_testing_and_performance, 03_architecture
Self-hosted раннер — Собственный (не предоставленный платформой CI) вычислительный сервер, используемый для запуска задач CI/CD, требующих специального оборудования — например, GPU.
См. также: 07_testing_and_performance
6. Предметная область: сейсморазведка
FDTD (Finite-Difference Time-Domain) — Метод конечных разностей во временной области — численный способ моделирования распространения волнового поля в среде, используется для генерации синтетических сейсмических данных.
См. также: BACKEND
Полноволновая синтетика — Синтетические сейсмические данные, сгенерированные с учётом полного волнового поля (все типы волн и их взаимодействия), а не упрощённой лучевой модели.
HRS (инженерная сейсмика) — Класс задач сейсморазведки для инженерных изысканий — обычно меньшего масштаба и объёма данных по сравнению с региональной или промысловой сейсморазведкой.
2D/3D проект — Тип сейсмической съёмки и последующей обработки по размерности регистрируемых данных: 2D — вдоль профиля, 3D — по площади, с кратно большим объёмом данных и вычислительной нагрузкой.
Сейсмическая трасса — Единичная запись колебаний, зарегистрированная одним приёмником (сейсмоприёмником) за время наблюдения — базовая единица сейсмических данных.
Геометрия наблюдений (survey geometry) — Пространственное расположение источников и приёмников при сейсмической съёмке, определяющее параметры последующей обработки и моделирования.
См. также: BACKEND
U-Net — Архитектура свёрточной нейронной сети, применяемая в проекте для задач денойзинга (шумоподавления) сейсмических данных.
См. также: 07_infrastructure_costs
Миграция (сейсмическая) — Класс алгоритмов обработки, восстанавливающих истинное пространственное положение отражающих границ по зарегистрированным сейсмическим данным.
Инверсия — Класс алгоритмов обработки, восстанавливающих физические параметры среды (скорости, плотности) по зарегистрированным сейсмическим данным.
